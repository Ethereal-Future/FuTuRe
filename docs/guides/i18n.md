# Internationalization (i18n) and RTL

This guide covers the full workflow for adding translatable strings, adding a new locale, the RTL/logical-properties CSS rules, and how the automated i18n checks fit into CI. It consolidates guidance that previously lived only in `CONTRIBUTING.md` or was scattered across the `frontend/src/i18n/` module itself.

---

## The i18n module

Translation is handled by [`i18next`](https://www.i18next.com/) / [`react-i18next`](https://react.i18next.com/), wired up in `frontend/src/i18n/index.js`:

- `SUPPORTED_LANGUAGES` — the list of locales the app ships, each with a `code`, display `name`, and text `dir` (`ltr`/`rtl`). This list drives the `LanguageSelector` dropdown (`frontend/src/components/LanguageSelector.jsx`) and language auto-detection — there's nothing else to register a locale in.
- `RTL_LANGUAGES` — the subset of codes that render right-to-left (`ar`, `he`). Used to set `document.documentElement.dir` on load and on language change.
- Initial language is chosen by `detectLanguage()` (`frontend/src/utils/detectLanguage.js`): a previously saved preference (`localStorage`, key `i18n_language`) wins, otherwise the browser's `navigator.languages` are matched against `SUPPORTED_LANGUAGES`, falling back to English.

In a component:

```jsx
import { useTranslation } from 'react-i18next';

function CopyButton() {
  const { t } = useTranslation();
  return <button title={t('copyButton.title')}>{t('copyButton.copied')}</button>;
}
```

To change the active language programmatically (as `LanguageSelector` does), call `i18n.changeLanguage(code)`, then persist it with `storeLanguage(code)` and update `document.documentElement.lang`/`dir` — see `LanguageSelector.jsx` for the full pattern, including updating `document.title` and the meta description tag.

### Locale-aware formatting

Don't format numbers, currency, dates, or relative times by hand — use `frontend/src/i18n/formatters.js`:

- `formatNumber(value, options, locale)`
- `formatCurrency(amount, currency, locale)`
- `formatDate(value, options, locale)` / `formatDateTime(value, locale)`
- `formatRelativeTime(value, locale)`
- `getLocaleCurrency(locale)` — maps a locale to its likely currency (e.g. `ar-AE` → `AED`)
- `formatXLMInput(value)` — the one exception: always formats with `.` as the decimal separator regardless of locale, because it feeds a value into blockchain APIs that must not be locale-ambiguous. Use this (not `formatNumber`) for raw XLM amounts in input fields.

All of these default to the current i18n language (or `navigator.language`) when no explicit `locale` argument is passed.

## Adding a translatable string

1. Add the key to `frontend/src/i18n/locales/en.json` (English is the source of truth). Keys are nested by namespace and read via dot notation, e.g. `"nav": { "install": "..." }` → `t('nav.install')`.
2. Add the same key, translated, to **every other** file in `frontend/src/i18n/locales/` (`ar.json`, `es.json`, `fr.json`, `he.json`, `pt.json`, `zh.json`). All locale files must have exactly the same key structure as `en.json` — no missing keys, no orphaned keys.
3. Use `t('your.key')` in the component via `useTranslation()`, not a hardcoded string literal in JSX. See [Running the i18n string check](#running-the-i18n-string-check) below for how this is enforced.
4. Run the test suite (`npm test`), which includes the locale-parity check described below.

See `frontend/src/i18n/locales/README.md` for the full key-naming convention, including the `stellarErrors` namespace used for Stellar/Horizon result-code messages.

## Adding a new locale

1. Create `frontend/src/i18n/locales/<code>.json` with the exact same key structure as `en.json` (copy `en.json` as a starting point and translate every value).
2. In `frontend/src/i18n/index.js`:
   - Import the new locale JSON.
   - Add it to the `resources` object passed to `i18n.init()`.
   - Add an entry to `SUPPORTED_LANGUAGES` with its `code`, `name` (in its own language), and `dir`.
   - If it's a right-to-left language, add its code to `RTL_LANGUAGES`.
3. That's it for wiring — `LanguageSelector` and `detectLanguage()` both read from `SUPPORTED_LANGUAGES`, so a new entry there is picked up automatically; no separate registration step exists.
4. Verify locale parity: `tests/i18n/locale-parity.test.js` runs automatically as part of the main test suite (`npm test` / `npm run test:coverage`) and fails if the new locale's keys don't exactly match `en.json`. `scripts/check-locale-parity.js` and `scripts/list-locale-diff.js` are standalone scripts for debugging a mismatch locally.
5. Manually verify RTL rendering if the new locale is right-to-left: switch to it via `LanguageSelector` and confirm layout mirrors correctly (see the RTL CSS rules below — a component using physical `left`/`right` properties instead of logical ones will not mirror even with `dir="rtl"` set correctly).

## RTL / logical-properties CSS rules

All new CSS must use **logical properties** instead of physical directional ones, so layouts mirror correctly for RTL locales (Arabic, Hebrew):

| Instead of | Use |
|---|---|
| `margin-left` / `margin-right` | `margin-inline-start` / `margin-inline-end` |
| `padding-left` / `padding-right` | `padding-inline-start` / `padding-inline-end` |
| `text-align: left` / `right` | `text-align: start` / `end` |
| `border-left` / `border-right` | `border-inline-start` / `border-inline-end` |
| positioning with `left` / `right` | `inset-inline-start` / `inset-inline-end` |

This is a manual convention — no lint rule currently enforces it (a stylelint rule such as `csstools/use-logical-properties-and-values` would be the natural way to automate it; see the code style guide's note on tooling gaps).

`RTL_LANGUAGES` in `frontend/src/i18n/index.js` and `LanguageSelector.jsx` are what set `<html dir="rtl">`; the logical CSS properties are what make that attribute actually change the visual layout. Both halves are required — setting `dir` alone does nothing for CSS that uses physical properties.

## Running the i18n string check

`scripts/check-i18n-strings.mjs` statically scans JSX under `frontend/src/components` for user-facing string literals (JSX text, `placeholder`/`title`/`alt`/`aria-label`/`aria-valuetext` attributes, and `msg.error/success/warning/info(...)` calls) that aren't routed through `t('...')`. New findings not already present in the checked-in baseline (`scripts/i18n-strings-baseline.json`) fail the check — this lets the existing backlog of hardcoded strings be paid down incrementally while still blocking *new* ones.

- Run locally: `npm run lint:i18n`
- **Runs in CI**: yes — `.github/workflows/ci.yml` runs `npm run lint:i18n` as a dedicated step ("Check for hardcoded i18n strings") on every PR.
- If a flagged string genuinely isn't user-facing copy (e.g. a CSS class name that happens to look like text), update the baseline with `node scripts/check-i18n-strings.mjs --write-baseline` rather than working around the check.

This check only covers `frontend/src/components` by default (`--dir` overrides it) and only flags *hardcoded* strings — it does not verify that translation keys actually exist in every locale file. That's what the locale-parity check (above) is for.
